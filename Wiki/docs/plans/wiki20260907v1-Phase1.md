# NoteBytez Wiki — Phase 1

## User Story

**As** a NoteBytez user — from someone who just installed it to a power user pushing Canvas,
Properties, and Plugins — **I want** a Wiki that gives me clear, step‑by‑step instructions for
every shipped feature, organised so I can either look up a single task or follow a worked
example for a workflow like mine, **so that** I can get productive quickly, trust that what I
read matches the app in front of me, and rely on it instead of guessing or asking for support.

**And as** the team shipping NoteBytez, **I want** that Wiki to be one Markdown source that
renders as a public, search‑engine‑ and AI‑retrieval‑friendly web site *and* backs contextual
"Help" links inside the app, kept honest by a release‑gated update step, **so that** it stays
accurate as the product evolves and does double duty as discoverable top‑of‑funnel content.

### Scope (Phase 1)

| In scope | Out of scope (later phase) |
|---|---|
| Public static web site generated from Markdown | Full in‑app article reader with its own nav/search |
| Contextual in‑app **Help** links that open the relevant web article | Video / narrated walk‑throughs |
| Step‑by‑step how‑to article for **every currently shipped user‑facing feature** (MVP + Version 1 + the V2 Enhancements + Subscription/Entitlement) | Advanced‑roadmap features not yet shipped (semantic index, AI assistant, publishing, Shortcuts) |
| Text + annotated screenshots (iPhone + Mac, light + dark) | iPad‑specific screenshots (layout differences described in prose) |
| 4 reader‑facing personas, one end‑to‑end journey each | Additional journeys per persona |
| Client‑side search on the web site (build‑time index) | In‑app search over bundled content |
| WCAG 2.2 Level AA conformance | AAA; formal third‑party certification |
| `en‑US` content in an i18n‑ready structure (`/en/…`, `hreflang`‑ready) | Translated locales |
| SEO + AI‑retrieval wiring (schema.org `HowTo`, `sitemap.xml`, `llms.txt`, semantic HTML) | Paid acquisition, backlink/off‑site SEO |
| Host‑agnostic build output | Choice of host and domain |

### Article standard

Every how‑to article MUST contain, in this order:

1. **Purpose** — one sentence: what the reader will accomplish.
2. **Applies to** — app version badge (`appliesTo` front‑matter, e.g. `1.0`) and platforms.
3. **Prerequisites** — state, permissions, or prior steps required.
4. **Steps** — a numbered `<ol>`; each major step pairs an action sentence with one annotated
   screenshot (`<figure>` + `<figcaption>` + descriptive `alt`).
5. **Expected result** — what the reader should see when done.
6. **Related** — cross‑links to adjacent how‑tos and the concept page(s) behind the feature.

Concept, reference, and journey pages are supporting page types with their own layouts; the
step‑by‑step how‑to is the primary one and the unit that content‑coverage is measured against.

## Personas

Four reader‑facing personas, deliberately lighter than the internal research set in
`NoteBytez/Docs/Plans/UIUX/01-Personas.md` (which stays the design‑research record). Each gets
exactly one end‑to‑end **journey** page in Phase 1 that threads the relevant how‑tos together.

| Persona | Who they are | Phase 1 journey |
|---|---|---|
| **The New Arrival** | Just installed NoteBytez, likely from Apple Notes or loose files. Needs the core capture loop and vocabulary. | *"Your first week"* — create a library, capture in the Journal, make your first `[[link]]` and `#tag`, find things again, understand sync status. |
| **The Switcher** | Moving from Obsidian or Logseq. Wants their vault in, their old habits mapped, and proof sync won't lose an edit. | *"Bring your vault across"* — run the Migration Assistant, verify links/tasks/Canvas imported, read the conflict‑strategy choice, keep the originals as a read‑only archive. |
| **The Power User** | Established user building structure. Pushing into Properties, Note Templates, Canvas, Saved Views, Graph insights, Plugins. | *"Model your world"* — define a Template Group, apply typed Properties, bind a Canvas board to a note, pin a Saved View, review Graph insights. |
| **The Collaborator** | Sharing a space with other people. Needs invitations, permission levels, and conflict etiquette. | *"Share a space"* — share a library, set per‑participant permissions, understand what read‑only vs read‑write means, resolve a multi‑party conflict. |

## Success Factors

Phase 1 is done when **all four** measurable criteria below pass. Each maps to a verification
gate in the Implementation Plan.

### SF1 — Content coverage (100%)

- Every currently shipped user‑facing feature in the Feature Inventory (below) has at least one
  published how‑to article.
- Every how‑to article passes the structure lint: front‑matter complete
  (`title, description, category, order, appliesTo[], personas[], featureSlug, lastReviewed,
  type`) **and** body contains all six required sections from the Article Standard.
- Every persona has one complete journey page; no journey links to a missing or draft article.
- Zero orphan pages — every page is reachable from the category nav and linked from at least
  one other page (mirrors NoteBytez's own "no orphan notes" principle).

### SF2 — Task completion (usability test)

- 5 participants (spread across the four personas) each attempt a fixed task list using **only**
  the Wiki — no other help, no guessing from the UI.
- **Target: ≥ 80% task‑completion rate** across all participant × task cells.
- Every failed task produces a specific content fix; the failed tasks are re‑tested and pass.

### SF3 — Accessibility audit (WCAG 2.2 AA, zero violations)

- Automated: `axe-core` and Lighthouse **Accessibility ≥ 95** on every published page, enforced
  in CI as a budget (build fails below threshold).
- Manual pass, all clear: keyboard‑only navigation; VoiceOver + Safari and NVDA + Firefox;
  200% zoom with no loss of content or function; 400% zoom reflow at 320 px width (WCAG 1.4.10);
  `prefers-reduced-motion` honoured; forced‑colors / high‑contrast mode legible.
- Specific 2.2 checks: visible focus never removed and never obscured (2.4.11); interactive
  targets ≥ 24×24 CSS px, primary controls ≥ 44 px (2.5.8); links distinguishable without
  colour, i.e. underlined in body copy (1.4.1); every status conveyed by icon + text, not
  colour alone (carried over from the app style guide).
- Result: **zero** outstanding WCAG 2.2 Level AA violations, signed off on the audit checklist.

### SF4 — SEO / AI‑retrieval checklist

- Valid `schema.org/HowTo` JSON‑LD on every how‑to (steps, tools, optional `totalTime`);
  `TechArticle` on concept pages; `BreadcrumbList` site‑wide; `WebSite` + `SearchAction`;
  `FAQPage` where a page is Q&A‑shaped. All validate in Google's Rich Results Test / the
  Schema.org validator.
- `sitemap.xml`, `robots.txt`, per‑page canonical `<link>`, per‑page meta description, Open
  Graph + Twitter Card tags.
- `llms.txt` at the site root plus per‑section index files; every page readable as static HTML
  with **no JavaScript required** for content (SSG output); clean, stable permalink slugs.
- Semantic HTML: one `<h1>` per page, ordered heading hierarchy, HTML5 landmarks
  (`header/nav/main/article/aside/footer`), skip‑to‑content link, `lang` on `<html>`,
  descriptive link text (no "click here"), `alt` on every non‑decorative image.
- Question‑shaped `<h2>`s with a concise answer in the first paragraph (helps featured
  snippets and LLM chunk retrieval alike).
- Lighthouse **SEO ≥ 95** and **Best Practices ≥ 95** on every page, enforced in CI.

### Derived Wiki Style Guide — deltas from `NoteBytez/Docs/styleGuide.md`

The app style guide is the parent. These are the **only** intentional departures, all to move
from a native SwiftUI context to an accessible static web context. To be promoted verbatim into
`Wiki/docs/styleGuide.md` in Phase 1.0.

| App style guide element | Web adaptation (WCAG 2.2 AA) |
|---|---|
| **Foundation** — "unapologetically native", HIG defaults | Web equivalent: system font stack (`-apple-system, BlinkMacSystemFont, "Segoe UI", …`), minimal custom chrome, honour `prefers-color-scheme` and `prefers-reduced-motion`. The site should read as *documentation for a native app*, not a marketing microsite. |
| **Typography** — SwiftUI Dynamic Type roles (`.largeTitle` … `.caption`), no fixed sizes | Fluid `rem` type scale; body ≥ 1rem (16 px) at `line-height` ≥ 1.5; measure ≤ 70 ch; role mapping — Large Title → `h1`, Title → `h2`/`h3`, Body → `p`, Callout → `.callout`, Caption → `<small>`. Must survive 200% zoom and 400% reflow (1.4.10) and a user text‑spacing override (1.4.12). |
| **Colour** — semantic system colours only (`.primary`, `.secondary`, `.accentColor`) | CSS custom properties mirroring the roles, both schemes. Light: primary `#000`; **secondary must be a solid `#5C5C66` or darker** — do *not* port the app's `#3C3C43 @ 60%`, it fails 4.5:1 on white. Accent `#0F766E` on white ≈ 5.4:1 (AA for normal text, not AAA) → **all body links underlined** (1.4.1), never colour alone. Dark: primary `#FFF`, accent `#2DD4BF`. Verify every token pair with a contrast check in CI. |
| **Accent used for links + active nav** | Body links always underlined. Focus ring `2px solid` accent at `2px` offset, never removed, never obscured (2.4.7 / 2.4.11). Active nav item marked with `aria-current="page"` **and** a non‑colour indicator (weight + rule). |
| **Status colours** — Success `.green` / Warning/Conflict `.orange` / Destructive `.red` | Keep the hues; every use pairs colour with an icon **and** a text label (the app's own rule). Admonition components (`Note` / `Tip` / `Warning`) carry `role`, icon, and visible label — never colour‑coded alone. Check each on light and dark for ≥ 3:1 non‑text contrast. |
| **Spacing & targets** — 8 pt grid, 44×44 pt minimum | 8 px spacing scale. Interactive targets ≥ 24×24 CSS px (2.5.8); primary controls (search field, pager, nav toggles) ≥ 44 px. Content column ~72 ch max. |
| **Iconography** — SF Symbols exclusively | Web uses **Lucide** (DD2) chosen to echo the in‑app symbols; ship the mapping table. Non‑decorative icons get an accessible name; decorative icons `aria-hidden="true"`. |
| **App icon / logo / Logo Text** (Arial Rounded MT Bold, `#0f454a`) | Reuse the NoteBytez wordmark as an **SVG** in the site header with a text alternative; do **not** depend on the proprietary font in CSS. `#0f454a` on white ≈ 10.6:1 — fine. |
| **Accessibility section** (VoiceOver, Dynamic Type, colour never the only signal) | Superset it with the web specifics: HTML5 landmarks, skip link, ordered headings, `lang`, keyboard operability, labelled search input with keyboard‑navigable results, tables with `<th scope>`, forms with associated `<label>` and error identification. |
| **(new) Motion** | Screenshots are static; if any animated media is ever added, no autoplay under `prefers-reduced-motion: reduce`, provide a first‑frame poster and an explicit play control. |
| **(new) Screenshots** | Generated from a documented Simulator seed library; each `<figure>` has a descriptive `alt` and `<figcaption>`; ≤ 1600 px wide, `loading="lazy"`, 2× asset for retina; annotation callouts use shape + label, not colour alone, at ≥ 3:1 against the screenshot. |

## Implementation Plan

TDD note (repo `CLAUDE.md` §8): the only behavioural code change is Phase 1.8's `helpURL(for:)`
map — its slug→URL resolution is unit‑tested first (red), then implemented. Everything else is
content + a static build verified by CI budgets and the four Success Factor gates.

Each phase states its verification. A phase isn't done until its verify step passes.

### Phase 1.0 — Foundations
- Record interview resolutions (this document) — done.
- Stand up the **Eleventy** project at `Wiki/site/` (DD1): minimal config, Nunjucks/Markdown,
  no client framework. Add **Pagefind** as a post‑build step.
- Create the repo layout (DD3): `Wiki/site/`, `Wiki/content/en/` (+ `_assets/`), `Wiki/docs/`.
- Promote the **Derived Wiki Style Guide** delta table above into `Wiki/docs/styleGuide.md`,
  cross‑referencing `NoteBytez/Docs/styleGuide.md` as parent.
- → **verify:** `npx @11ty/eleventy` builds an empty site; Pagefind runs; style guide reviewed
  line‑by‑line against the app guide with every WCAG 2.2 AA mapping present.

### Phase 1.1 — Information architecture
- Lock the category taxonomy (the Feature Inventory's left column).
- URL scheme: `/en/<category>/<article-slug>/`, stable permalinks, no dates in slugs.
- Front‑matter schema, enforced by an 11ty data check / JSON Schema:
  `title, description, category, order, appliesTo[], personas[], featureSlug, lastReviewed,
  type (howto | concept | reference | journey)`.
- Navigation model: persistent category tree + breadcrumb + per‑article Related + four persona
  journey hub pages.
- → **verify:** every feature in the Feature Inventory maps to ≥ 1 planned article slug; every
  `featureSlug` is unique; taxonomy review sign‑off.

### Phase 1.2 — Templates & components
- Page layouts: `howto`, `concept`, `journey`, `reference`.
- Components: admonition (role + icon + label), numbered step list, screenshot `<figure>`,
  "Applies to" badge, prev/next pager, breadcrumb, skip‑to‑content link, persona chip.
- JSON‑LD partials: `HowTo`, `TechArticle`, `BreadcrumbList`, `WebSite` + `SearchAction`,
  `FAQPage`.
- Pagefind search UI: labelled input, keyboard‑navigable results, correct ARIA.
- Base template: HTML5 landmarks, one `h1`, `lang="en"`, canonical, meta description, OG/Twitter.
- → **verify:** `axe-core` + Lighthouse on the template/sample pages ≥ 95 accessibility **and**
  ≥ 95 SEO; all JSON‑LD passes the Rich Results Test.

### Phase 1.3 — Screenshot pipeline
- Author a fixed Simulator **seed library** (a committed fixture `.md` set).
- Capture script: `xcrun simctl` / the iOS Simulator control, iPhone 17 Pro + "My Mac",
  light + dark; output to `Wiki/content/en/_assets/<category>/`.
- Naming + retina (`@2x`) convention documented in the style guide.
- → **verify:** one category's screenshots regenerate byte‑for‑stable from the script on a
  clean machine.

### Phase 1.4 — Content authoring (the bulk of the work)
- Write every how‑to in the Feature Inventory, category by category, to the Article Standard.
- Write the four persona **journey** pages, each threading its how‑tos end to end.
- Write the supporting **concept** pages (sync model, blocks & anchors, three conflict
  strategies compared, entitlement model, "your data is plain Markdown") and **reference**
  pages (Markdown syntax table, keyboard shortcuts, glossary, SF Symbol index).
- Internal linking pass — no orphan pages.
- → **verify:** SF1 — content‑coverage checklist 100%; structure lint passes on every article;
  no journey links to a missing/draft page; link‑checker (internal + external) clean.

### Phase 1.5 — SEO / AI‑retrieval wiring
- `sitemap.xml`, `robots.txt`, per‑page canonical + meta description, OG/Twitter tags.
- `llms.txt` at root + per‑section index files; verify every page is readable with JS disabled.
- Question‑shaped `<h2>`s with the answer in the first paragraph; descriptive link text audit.
- → **verify:** SF4 — schema validates site‑wide; `llms.txt` resolves; Lighthouse SEO ≥ 95 and
  Best Practices ≥ 95 on every page; no page requires JS to read.

### Phase 1.6 — Accessibility audit
- CI budgets: `axe-core` + Lighthouse Accessibility ≥ 95 on **every** page (build fails below).
- Manual pass: keyboard‑only; VoiceOver + Safari; NVDA + Firefox; 200% zoom; 400% reflow at
  320 px; `prefers-reduced-motion`; forced‑colors. Fix to zero.
- 2.2‑specific checks: 2.4.11 focus not obscured, 2.5.8 target size, 1.4.1 colour‑only links.
- → **verify:** SF3 — signed audit checklist, zero WCAG 2.2 AA violations, CI gate green.

### Phase 1.7 — Usability test
- 5 participants across the four personas; fixed task list; Wiki‑only.
- Log every failure → specific content fix → re‑test.
- → **verify:** SF2 — ≥ 80% task completion; previously failed tasks pass on re‑test; report
  filed under `Wiki/docs/`.

### Phase 1.8 — In‑app contextual Help links
- Unit test first: `helpURL(for: FeatureSlug) -> URL` resolves every shipped slug to a stable
  permalink; unknown slug → `nil` (red before implementation).
- Implement the map + add Help affordances to screens whose feature has a published article
  (open `SFSafariViewController` on iOS, default browser on macOS). New `.swift` files carry the
  `CLAUDE.md` §11 copyright header. No new dependency; no analytics.
- → **verify:** each linked screen opens the correct live article; `NoteBytezTests` stays green;
  no duplicated URL string literals (all via the map).

### Phase 1.9 — Build, CI, and the release gate
- CI pipeline: build site → axe + Lighthouse budgets (a11y/SEO/Best‑Practices ≥ 95) → HTML
  validate → link‑check → JSON‑LD validate → Pagefind index → publish `Wiki/site/_site/`.
- **Release gate (R5):** add to the app release checklist — "update affected Wiki articles and
  bump `appliesTo`"; add a PR‑template checkbox; add a CI check that a PR touching a feature
  plan doc under `NoteBytez/Docs/Plans/` also touches `Wiki/content/en/**` **or** carries an
  explicit `wiki-none` label.
- Host‑agnostic output; actual deploy target deferred (DD8) — dry‑run deploy to a preview URL.
- → **verify:** CI green on a sample content PR; release checklist + PR template updated;
  preview deploy renders correctly.

### Phase 1.10 — Definition of Done
- SF1, SF2, SF3, SF4 all pass.
- `Wiki/docs/styleGuide.md` promoted and reviewed.
- In‑app Help links live for every covered screen.
- Release‑gate CI check active.
- No open items in Gaps and Resolution except deliberately deferred DD8 (host/domain).
