#  User Story
As a User of the NoteBytez app, I want to be able to identify when I have resolved syncing issues between users and devices, so that I can trust that my resolution took effect and know that I have not silently lost an edit.

- "Syncing issues" covers both multi-device conflicts on my own account and multi-user conflicts in a library shared with other people. Multi-user is the priority case.
- When a conflicting version came from a collaborator, the confirmation names them ("kept Dana's version"), not just "synced elsewhere".
- "Identify when I have resolved" means three concrete signals: (a) each conflict I act on is acknowledged in place, (b) the sync glyph returns to green with a calm all-clear once every conflict is gone, and (c) a durable history entry records what I kept.
- A resolution I made by hand is briefly undoable, the same guarantee the automatic Last-Write-Wins path already gives.

## Current Experience
1. When a syncing issue is identified, the sync symbol on screen changes from the green circular arrow sync icon to the yellow triangle sync warning icon to indicate to the user that a sync issue needs to be addressed.
2. The user selects the yellow triangle sync warning icon.
3. The system displays the Sync Status panel.
    - The sync status window shows the number of note items with a conflict.
    - The sync status window shows the conflict item labels in the 'Needs Your Attention' section.
3. The user selects the item to resolve.
4. The system displays the Conflict panel.
5. The user is presesnted with the conflicts to choose which one to keep, or may elect to keep both versions.
6. The user selects one of the options - 'Keep This Version'.
7. No indicator appears on the screen to show that the issue has been resolved.
8. When the user returns to the Sync Status panel, the Conflict is still listed.
9. When the user exits the Sync Status panel, the yellow warning icon is still shown.

## New Experience
1. When a syncing issue is identified, the sync symbol on screen changes from the green circular arrow sync icon to the yellow triangle sync warning icon to indicate to the user that a sync issue needs to be addressed.
2. The user selects the yellow triangle sync warning icon.
3. The system displays the Sync Status panel.
    - The sync status window shows the number of note items with a conflict.
    - The sync status window shows the conflict item labels in the 'Needs Your Attention' section.
3. The user selects the item to resolve.
4. The system displays the Conflict panel.
5. The user is presesnted with the conflicts to choose which one to keep, or may elect to keep both versions.
6. The user selects one of the options - 'Keep This Version'.
7. The system should visually identify to the user that their selection has been made and that changes are being applied to the item in question.
8. When the user returns to the Sync Status panel, the Conflict is still shown in the 'Needs Your Attention Section' - once the user has made aa selection to resolve the issue, it should be removed from the 'Needs Your Attention' section.
9. When the user exits the Sync Status panel, if all items have been resolved, the sync icon should change to the green circular arrow.

# Success Factors
1. When conflicts are resolved, the system will provide a visual indicator to the user that the selected/preferred resolution is being recorded.
2. When conflicts are resolved, the system will remove the conflict form the 'Needs Your Attention' on the Sync Status panel.
3. When conflicts are resolved, the system will show the proper sync status indicator - green or yellow, depending on whether all issues have been resolved.
4. Each resolved conflict is acknowledged in place: its row in 'Needs Your Attention' shows a "Resolved" state with a checkmark for roughly 1.5 seconds, then animates out. When it was the last conflict, the section is replaced by a calm empty state - "No conflicts — you're all synced".
5. The Conflict panel dismisses itself automatically once the user makes a resolution choice, returning the user to the Sync Status panel where the acknowledgement is shown.
6. Every resolution writes a durable entry to the 'Recent Activity' log stating which side was kept: "kept this device's edit", "kept {collaborator name}'s version" (falling back to "the version synced elsewhere" when no name resolves), or "kept both versions".
7. For roughly 5 seconds after a manual resolution, an "Undo" affordance is shown where the resolution happened. Undo restores the conflict to 'Needs Your Attention' and, when live sync is running, re-applies the pre-resolution record.
8. A resolution is acknowledged only if it actually succeeded. If applying it fails, no "Resolved" indicator or success log entry appears; the existing inline error banner with Retry is shown and the conflict stays listed.
9. The glyph, the status headline ("Conflict on N notes"), the conflict count, and the 'Needs Your Attention' list are always consistent with one another - resolving a conflict clears it from every surface together, never from only one.
10. Accessibility: the acknowledgement is carried by icon plus text, not color alone, and is announced to VoiceOver; the sync glyph keeps its VoiceOver label in every state.

# Gaps and Resolutions

Gaps found while reviewing the User Story and Success Factors above, and how the interview on 2026-09-10 resolved each. Success Factors 4-10 and the User Story clarifications were added as a result.

1. **"Between users and devices" was undefined.** Could mean shared-library (multi-user) conflicts, single-account multi-device conflicts, or both.
   - Resolution: Both, with multi-user as the priority. The resolution feedback must attribute a kept server version to a named collaborator when the conflict originated from one, reusing the collaborator name already derived in `Conflict.revisions`.
2. **The User Story had no benefit clause and no definition of "identify ... resolved".**
   - Resolution: The benefit is trust that the resolution took effect - the personas' "never silently lose an edit". "Identify" was pinned to three signals: per-conflict acknowledgement, all-clear return to the green glyph plus an empty state, and a durable history entry.
3. **Success Factors covered removal and the glyph but not the moment of resolution, the empty state, or the Conflict panel's own behaviour.**
   - Resolution: Added SF 4 and SF 5 - the resolved row shows "Resolved ✓" for ~1.5s then animates out; the last one gives way to "No conflicts — you're all synced"; the Conflict panel auto-dismisses back to the Sync Status panel on choice (today it stays open).
4. **No audit trail of resolutions was required.**
   - Resolution: Added SF 6 - every resolution logs to 'Recent Activity' with the kept side and collaborator attribution. A pure, testable summary function derives the text from the choice and the conflict.
5. **Manual resolutions had no undo.** Only the automatic Last-Write-Wins path exposes a Revert today.
   - Resolution: Added SF 7 - a ~5 second "Undo" toast shown where the resolution happened. Undo re-queues the conflict and, when a live engine is running, re-saves the pre-resolution record. A time-pressured toast (not a persistent list) was chosen deliberately; the automatic path keeps its existing Revert.
6. **Defect found in testing (2026-09-10): resolution state is not atomic.** `ConflictResolutionViewModel.resolve` calls `SyncStatusStore.decrementConflictCount()` unconditionally, but `SyncEngine.resolveConflict` returns early - before `ConflictStore.remove` - whenever no live `CKSyncEngine` is running. The glyph count drops while the 'Needs Your Attention' row and the queued `Conflict` remain. Steps 8-9 of "Current Experience" are partly this defect, not only missing UI.
   - Resolution: In scope for this bug. The store-clear must not be gated on a live engine; `ConflictStore`, `SyncStatusStore`, and the Sync Status / glyph views are reconciled so a resolved conflict leaves every surface atomically (SF 9). This also makes the `-SeedTestConflicts` fixture fully exercisable without `-EnableLiveSync`.
7. **The failure path was undefined** - what the user sees if the resolution save fails.
   - Resolution: Added SF 8 - no false acknowledgement; the existing inline error banner with Retry is shown and the conflict stays listed.
8. **No accessibility requirement for the new feedback.**
   - Resolution: Added SF 10 - icon plus text, never colour alone, with a VoiceOver announcement, per the design system's "color is never the only signal" rule.
9. **Terminology:** the document says "yellow triangle". The implemented and design-system colour is orange `exclamationmark.triangle` (`.orange`, deliberately not red because a conflict is recoverable). No behaviour change - noted so the two read the same.
10. **Explicitly out of scope** (raised, then dropped in the interview): a partial-progress counter such as "1 of 2 resolved"; any change to conflict *detection*; the cross-account `CKShare` acceptance blocker tracked separately in the Phase 4 live-sync notes.

# Implementation Plan

MVVM, TDD - each phase writes or extends a failing test first, then makes it pass. File paths are the current sources under `NoteBytez/`. Phase 0 and Phase 1 are the load-bearing fixes (the atomicity defect); the rest is additive UX.

### Phase 0 - Reproduce (red tests)
1. `NoteBytezTests/SyncEngineTests.swift` + `ConflictStoreTests.swift`: after `SyncEngine.resolveConflict(_:choice:in:)` with no live engine, assert `ConflictStore.shared.conflicts` is empty **and** `SyncStatusStore.shared.conflictCount` decremented.
   -> verify: new assertions fail on the store-clear today.
2. `NoteBytezUITests/Phase1ConflictResolutionSmokeTests.swift`: launch with `-SeedTestConflicts`, resolve "Draft Proposal", assert the 'Needs Your Attention' row disappears and the headline goes to "Conflict on 1 note".
   -> verify: fails today (row persists).

### Phase 1 - Make resolution state atomic
1. `NoteBytez/sync/SyncEngine.swift` - in `resolveConflict`, split the "no live engine/database" case out of the bare early `return`: always run the local model apply, `ConflictStore.shared.remove(conflict)`, and `clearAutoResolution(syncId:)`; only the CloudKit `save` is guarded by the live-engine check.
2. `NoteBytez/viewModels/ConflictResolutionViewModel.swift` - remove the standalone `SyncStatusStore.shared.decrementConflictCount()` call; fold the count decrement into the same single writer in `SyncEngine` so the count and the list cannot diverge.
3. `NoteBytez/sync/SyncStatusStore.swift` - keep `decrementConflictCount()` defensive (never below `ConflictStore.shared.conflicts.count`); add `incrementConflictCount()` for Phase 4.
   -> verify: Phase 0 tests green; existing `SyncEngineTests` / `ConflictResolverTests` / `JourneyIntegrationTests` (Journey 3) still green; `SyncStatusViewModel.statusTint` returns `.success` once the last conflict clears (already derived from `conflictCount`).

### Phase 2 - Per-conflict acknowledgement + panel auto-dismiss
1. `NoteBytez/sync/ConflictStore.swift` - add `recentlyResolved: [UUID: ResolvedAck]` (`@Observable`), populated on resolve and cleared by a ~1.5s `Task`. `ResolvedAck` carries `syncId` and the kept-side label.
2. `NoteBytez/views/Sync/SyncStatusView.swift` - when a row's `syncId` is in `recentlyResolved`, render `Label("Resolved", systemImage: "checkmark.circle.fill")` in green with an opacity transition; give the "Needs Your Attention" section the design-system empty state ("No conflicts — you're all synced") when `conflicts` is empty (today only "Recent Activity" has one).
3. `NoteBytez/views/Conflict/ConflictResolutionView.swift` - on a successful `resolve`, call `@Environment(\.dismiss)` so the panel pops back to the Sync Status panel; do not dismiss on failure.
   -> verify: UI test - resolve in the Conflict panel -> panel dismisses, Sync Status shows "Resolved ✓" then the row leaves; resolving the last one shows the empty state and a green glyph. Screenshot on iPhone + iPad sims via `-SeedTestConflicts`.

### Phase 3 - Resolved-history log entry with attribution
1. `NoteBytez/sync/Conflict.swift` - add a pure `resolutionSummary(for choice: ConflictResolutionChoice) -> String`: `.keepClient` -> "kept this device's edit"; `.keepServer` -> "kept {collaborator}'s version" or "kept the version synced elsewhere"; `.keepBoth` -> "kept both versions"; `.merged` -> "kept a merged version". Promote the existing private `collaboratorName(for:)` as needed.
2. `NoteBytez/sync/SyncStatusStore.swift` - add `recordManualResolution(title:summary:)` -> log `Resolved — "{title}" — {summary}` (non-error). `SyncEngine` calls it from the atomic block in Phase 1.
   -> verify: `ConflictTests` - `resolutionSummary` names the collaborator when keeping the server side, falls back with no name, and handles keep-both / keep-this / merged. Pure, no CloudKit. 'Recent Activity' shows the line after a resolve.

### Phase 4 - Undo window for manual resolutions
1. `NoteBytez/sync/ConflictStore.swift` - add `pendingUndo: ConflictResolutionUndo?` (snapshot of the `Conflict` + `choice` + timestamp), auto-cleared by a ~5s `Task`.
2. New `NoteBytez/views/Components/UndoToast.swift` - styled like `ConflictBanner`; shown in `SyncStatusView` and, when the resolution happened there, atop `DocumentView` (parallel to the existing `ConflictBanner` slot). One at a time.
3. Undo action: `ConflictStore.queue(undo.conflict)`, `SyncStatusStore.incrementConflictCount()`, and `SyncEngine.reapplyPreResolution(_:)` which re-saves `undo.conflict.serverRecord` (carries the change tag) when a live engine exists; local re-queue only otherwise. Log an `Resolution undone — "{title}"` activity row.
   -> verify: `ConflictStoreTests.undoRequeuesConflictAndRestoresCount`; UI test on `-SeedTestConflicts` - resolve, tap Undo within the window, conflict is back in 'Needs Your Attention', count restored, glyph orange again.

### Phase 5 - Multi-user attribution, end to end (manual, sandbox-only)
1. Confirm `serverRecord.lastModifiedUserRecordID` -> `SharingPermissionStore.displayName` resolves for a real shared-library conflict. Add a `-SeedTestConflicts` knob to stub a display name via `SharingPermissionStore` for visual QA (the synthetic fixtures cannot carry a real `lastModifiedUserRecordID`).
2. Manual verification only, per the Phase 4 live-sync notes: two simulators on the same Apple ID, or the add-by-email path from `NoteBytez20260831v1-Sharing.md`.
   -> verify: live - a collaborator conflict resolved on device A logs `Resolved — "…" — kept {B}'s version`. Documented as manual, Development/Sandbox only.

### Phase 6 - Accessibility & polish

Post a VoiceOver announcement on resolve ("Conflict resolved, kept this device's edit"); `accessibilityLabel` on the "Resolved ✓" row; ensure the `UndoToast` Undo button is labelled and, while VoiceOver is running, is not auto-dismissed out from under focus (extend the window under `UIAccessibility.isVoiceOverRunning`).
